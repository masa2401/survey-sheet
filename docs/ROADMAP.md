# ロードマップ

## 目的

- 汎用のアンケートアプリを、管理者が自分でデプロイして使える形で配布する
- 管理者は設問定義ファイルと環境変数を用意し、起動するだけで使い始められる
- スキルシート作成アプリは、このアプリの利用例の1つとして扱う

## 基本構成

- アプリを、機能（エンジン）と設問定義（コンテンツ）に分ける
- 1つのインスタンスで扱うアンケートは1テーマ
- 運用は、イベントごとに設問を決めて使う想定。版が変わるのは、誤字の修正などに限られる
- 回答形式（チェックと5段階評価）、画面の流れ、結果表示、CSV、共有は、現在の機能をそのまま使う
- 役割分担：フロントは表示と状態の管理だけを受け持ち、それ以外のロジックはバックエンドで処理する
  - フロントを別の仕組みで作り直しても、バックエンドをそのまま使える形にする
  - フロントは、API から受け取ったものを当てはめて表示する。変換の処理は持たない
  - 規則（入力の検証の規則など）の置き場所は1か所にする。入力中のエラーの判定はフロントで行い、規則はバックエンドから受け取る
- 配布するのは、バックエンドを Go で実装した版。Spring Boot 版は機能を固めるための実装として使い、配布しない
- 画面は日本語で実装する。英語版は、配布の段階で別の版として配布する

## 設問定義

- 定義ファイルを唯一の正とする
  - 最小構成では、管理画面と管理者の認証は持たない。形になってから、管理画面の追加を検討する
  - DB には、回答を、回答したときの文言つきで保存する
- 管理者は、Docker や基本的なインフラを扱える技術者を想定する
- 設定は、設問の定義（`survey.json`）と表示設定（`display.json`）の JSON の2ファイルに分ける
  - 表示設定は、バックエンドが既定値を当ててフロントに返す。それ以外の画面の文言は、アプリに固定で持つ
- 定義ファイルは `surveys/<名前>/` に置き、使うフォルダを環境変数で選ぶ
- JSON Schema は `schema/` に置く。配布物でも同じ位置関係にする
- 尺度は5段階で固定する
- サンプル定義を2種類同梱する（スキルシートと、別のテーマを1つ）
- 版は、設問の定義ファイルの内容から計算したハッシュ値で識別する
- 検証は、エディタ（JSON Schema）・コミット時のテスト・起動時の3段で行い、同じ規則を使う。間違いがあれば起動を止める
- 細かい内容は `DECISIONS.md` に書く

## 配信と任意機能

- 既定は同一デプロイ（バックエンドが画面も配信する）
- 環境変数を設定した場合のみ、フロントを別にデプロイできる
- PDF は、バックエンドが PDF 用のコンテナ（Gotenberg）に描画を頼んで生成する。PDF 用のコンテナは compose に並べる
- Spring Boot 版は、環境変数で描画役を Lambda に切り替えられる
- シートは、URL 共有・PDF・CSV の操作のときに保存する。期限の日数は管理者が設定する
- PDF は、PDF のボタンを押したときに生成する
- CSV は、バックエンドが保存したシートから作る
- バックエンドなしで動くモードはやめる。回答そのものを URL に入れるクエリ方式の共有は削除する

## 段階

1. 新しいリポジトリを作る（完了）
2. 定義の形とコンテンツの範囲を決め、JSON Schema を作る
3. フロントを、定義から画面を組み立てる形に整理する
4. 定義をバックエンドに移す（読み込み・検証・版・API）
   - マイグレーションを1つの V1 にまとめ直し、新しいテーブルで始める
   - e2e テストを、バックエンドありの形に変える
5. 同一デプロイと別デプロイの切り替え、PDF の描画役（PDF 用のコンテナ・Lambda）の切り替えを作る
6. 公開中のスキルシートを、このリポジトリからの配信に切り替える
   - 新しい DB に切り替える。旧アプリの回答は引き継がない
   - バックエンドを先に、フロントを後に切り替える
7. バックエンドを Go で置き換える
   - 既存の DB を引き継ぐ場合は、Flyway の適用履歴の扱いを決める
8. 配布用に整備する（`docker compose`、設定の説明、定義ファイルの検証コマンド）

段階1〜6は Spring Boot 版で進める。

段階3と4は同時に検討する。実装は、バックエンドの定義の API を先に作る。
