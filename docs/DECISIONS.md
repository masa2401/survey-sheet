# 決定事項

日常の作業で守るルールは `.claude/rules/` にまとめている。\
この文書には、方針に関わる決定と、ルールに書ききれない理由を残す。

## 2026-10-31 汎用アンケートアプリへの移行

- 汎用化すると、アプリの中身が旧リポジトリ名（CreateSkillSheet）と食い違う。\
  そのため、ブランチではなく新しいリポジトリ（survey-sheet）に切り出した。
- 旧リポジトリのコミット履歴を引き継いだ。\
  方針転換の経緯を、履歴から追えるようにするため。
- 設問の差し替えは、管理者が定義ファイルを編集して再起動する形にする。\
  管理者が自分でデプロイする前提なら、画面からの編集機能と認証は不要なため。
- 設問を差し替えたら、以前の回答は使えなくする。\
  古い回答を古い定義で表示し続ける仕組みより、単純に保てるため。
- 定義ファイルの検証規則は1か所で実装し、テストと起動時で共用する。\
  規則が2か所に分かれると、片方だけ直して食い違う原因になるため。
- 配信は同一デプロイを既定にする。\
  導入が簡単で、フロントとバックエンドの反映のずれも起きないため。
- Node と Java のバージョンは `.nvmrc` と `.java-version` で指定する。\
  開発環境では Node を nvm、Java を OS のパッケージで入れており、\
  新しいツールを入れずに済むため。CI も同じファイルを参照する。
- `deploy.yml` は、手動実行のみにしている。\
  このリポジトリには、本番のデプロイ先をまだ設定していないため。
- `DESIGN_NOTES.md` は削除する。\
  旧リポジトリはポートフォリオとして設計を説明する目的だったが、\
  このリポジトリは配布が目的のため。
- `README.md` は、利用者が自分の環境に構築するための手順書にする。

## 2026-11-02 バックエンドの実装

- 配布するのは Go 版にし、Spring Boot 版は配布しない。\
  Spring Boot は常駐時のリソース消費が大きく、管理者が自分の環境で動かす配布形態に向かないため。
- Go への置き換えは、アプリの大枠を Spring Boot 版で完成させた後に行う。\
  置き換えにかかる作業量をまだ見積もれないため。
- 配布用の整備（ROADMAP の段階8）は、Go に置き換えた後に行う。\
  配布しない Spring Boot 版で整備しても、作り直しになるため。

## 2026-11-04 設問の定義と表示設定（段階2）

- 設定は、設問の定義（`survey.json`）と表示設定（`display.json`）に分ける。\
  版のハッシュは設問の定義だけで計算し、文言やアイコンを直しても回答が無効にならないようにするため。\
  回答の意味が変わるものを設問の定義に、変わらないものを表示設定に置く。
- 表示設定は、ビルド時ではなく画面を開いたときに読み込む。\
  管理者はビルド済みのイメージを使い、フロントをビルドし直さないため。
- ファイル形式は JSON にする。\
  将来 GUI の設定ツールを作る場合に、ツールから書き出しやすいため。\
  手で書きにくいという問題が出たら、YAML への対応を検討する。
- 尺度の名前と説明は、表示設定に置く。\
  回答は1〜5の数値で保存し、バックエンドは範囲しか見ないため。\
  尺度の説明を書き換えても版は変わらず、保存済みの回答は新しい説明で表示される。
- グループは、全員が回答する `alwaysShownGroups` と、\
  回答者が TOP で選んだときだけ出す `selectableGroups` の2つの配列に分ける。\
  構造を見ただけで違いが分かり、管理者が間違えにくいため。\
  コード内の `isCheckedByDefault` は改名せず、読み込むときに変換する。
- グループの `id` は、管理者が文字列で書く（例：`engineer`）。\
  表示設定のアイコンがグループを `id` で参照するため、並び順に頼らない名前が必要になる。\
  文字列にすると表示設定が読みやすくなり、今の数値の `id` と `key` の二重管理もなくなる。\
  HTML の `id` 属性にも使うので、JSON Schema で使える文字を制限する。
- グループの `id` は、2つの配列をまたいで重複させない。\
  保存した回答がグループの `id` で参照するため。
- 設問と項目には `id` を書かない。アプリが配列の順序から番号を振る（1始まり、親の中で振り直す）。\
  `id` を振り直さない制約は、保存済みのシートと共有 URL のためのものだった。\
  版が変わると両方とも無効になるので、管理者が番号を管理する理由がなくなる。\
  DB には今と同じく、振った番号を integer で保存する。親子の結び付きは DB の連番が担うので、テーブルの構造は変わらない。
- 番号を振るものは、必ず配列で書く。\
  JSON のオブジェクトはキーの順序が決まっておらず、Go の `map` は読み込むたびに順序が変わり、\
  Node.js は数字のキーを先頭に並べ替える。配列の順序は、どの言語でも保たれる。
- 番号を振る処理は1か所にする。段階3ではフロントが振り、段階4からはバックエンドが振って API で渡す。\
  フロントとバックエンドで規則が食い違わないようにするため。
- 回答者の名前の入力は、必須のまま残す。\
  名前を確定しないと共有などの機能を使えない、という今の作りを保つため。\
  結果ページの見出しと CSV のファイル名は、表示設定で `{name}` を含むテンプレートとして書く。\
  「様」だけを別の項目にするより、語順の違う言い回しにも対応できるため。
- 文言は、アプリに汎用的な既定値を持たせ、表示設定に書いた項目だけを上書きする。\
  アプリの更新で項目が増えても、管理者の古い表示設定がそのまま使えるようにするため。\
  オブジェクトはキーごとに、配列（尺度の説明など）は丸ごと置き換える。
- 固定の文言は、「スキルシート」「習熟度」などの名詞を表示設定で入れ替えて組み立てる。\
  文ごとに上書きできる形より、設定の項目を少なく保てるため。
- 回答そのものを URL に入れるクエリ方式の共有（`#/result?data=`）は削除する。\
  バックエンドのデプロイに失敗した場合に備えて残していたが、\
  今後はフロントとバックエンドをまとめて配布するため。
- アイコンは任意にし、指定のないグループには表示しない。\
  アイコンがなくても成り立つデザインにし、管理者が足すと見た目が豊かになる形にするため。
- アイコンは表示設定で、グループの `id` に Lucide の名前か、\
  管理者が用意した SVG（`custom/` で始まる名前）を結び付ける。\
  SVG ファイルを配信し、CSS のマスクで文字色の単色として表示する。\
  `@lucide/vue` を名前で動的に読み込むと、対応表だけで最初の JS が約90KB（gzip）増えるため。\
  マスクなら、管理者の SVG も同じ仕組みで扱え、SVG 内のスクリプトも実行されない。

## 2026-11-05 定義ファイルの検証（段階2）

- 検証の対象は、OSS の管理者が定義ファイルを編集するときの書き間違い。\
  そのため、配布する完成形（Go 版）を前提に決める。段階4より前は、エディタでスキーマが効けば足りる。
- 形の検証は JSON Schema、スキーマで表せない規則はバックエンドのコードで行う。\
  コードはバックエンドの検証処理の1か所に置き、起動時・検証コマンド・CI のテストから同じ処理を呼ぶ。\
  フロントは、起動時の検証を通った定義だけを受け取る前提にし、検証しない。
- バックエンドは起動時に `display.json` も検証し、検証した内容が正しければ、そのままフロントに返す。\
  文言やアイコンを画面に反映するのはフロントだけ。\
  `display.json` の変更は、`survey.json` と同じく再起動で反映される。\
  フォルダのファイルを直接配信すると、起動後に書き換えた内容が、検証を通らずに画面へ届くため。\
  アイコンのグループへの参照のように、2つのファイルにまたがる規則を確かめられるのもバックエンドだけになる。
- 管理者が用意する SVG アイコン（`custom/`）は、フォルダから配信する。\
  起動時にファイルがあるかを確かめる。起動後に消された場合は、アイコンが出なくなるだけで画面は壊れない。
- 間違いが1つでもあれば、起動を止める。
- 定義ファイルの `$schema` は相対パスで書き、スキーマのファイルを配布物に同梱する。\
  URL にすると、アプリの更新で参照先を書き換えたときに定義ファイルのバイト列が変わり、版が変わるため。
- 起動時と検証コマンドのエラーメッセージは、日本語で組み立てる。\
  検証ライブラリは違反の種類と値（例：必要な件数と実際の件数）をデータとして返すので、そこから文を作る。\
  英語の既定のメッセージ（例：`minItems: got 0, want 1`）は、管理者に伝わりにくいため。
- `pattern` を使う項目には、VS Code の拡張の `patternErrorMessage` を付ける。\
  `does not match pattern` だけでは、何が悪いのかが伝わらないため。\
  Draft 2020-12 では知らないキーワードは無視されるが、次の版（v1）では許されなくなるとされている。\
  v1 に移行するときは、この書き方が使えるかを確かめ直す。
- `pattern` の正規表現は、先読み（`(?=...)`）などを使わない単純な書き方にとどめる。\
  Go の標準の正規表現は先読みに対応しておらず、言語によって結果が変わるため。

## 2026-11-05 名前・上限・DB（段階2）

- 3つの階層の名前を `groups`（グループ）→ `questions`（設問）→ `items`（項目）にする。\
  `categories` と `answers` は、スキルシートを前提にした名前だったため。\
  `groups` は意味の範囲が広く、部署ごとにアンケートを使い分けるような使い方にも合う。\
  LimeSurvey（question group）や XLSForm（group）も、同じ単位を group と呼んでいる。
- 項目を `answers` と呼ばない。\
  管理者には「回答」と読め、保存された回答（`sheet_answers`、`AnswerDto`）と同じ言葉になるため。\
  同じ尺度で複数の行を評価させる形式で、LimeSurvey も Qualtrics も、行を評価する項目として扱っている。
- 2つの配列は `alwaysShownGroups` と `selectableGroups` にする。\
  `common` は「一般的な」とも読め、`optional` は「回答しなくてよい」とも読めるため。\
  汎用のアンケートツールは、グループの種類ではなく表示の条件で区別しているので、挙動を表す名前にする。\
  `selectable` は、`TopPage.vue` の `selectableCategories` にも前例がある。
- グループの名前は `label`、設問の見出しは `title` のまま変えない。\
  今のコード（`CategoryMaster.label`、`QuestionMaster.title`、`ValidationErrorItem`）と揃っているため。
- 名前を変えるのは、まず JSON だけにする。読み込むときに今の型に変換する。\
  コード（型・テスト・e2e のロケーター `data-slot="category-card"` など）と DB の名前は、\
  段階3と段階4で置き換える。置き換える範囲が広いので、作業のたびに範囲を確認してから進める。
- `display.json` は、複数の画面で使うもの（`appName`・`terms`・`scale`・`respondent`・`groupIcons`）と、\
  画面ごとのもの（`top`・`result`・`csv`）に分ける。どこを直せば画面のどこが変わるかを分かりやすくするため。\
  見出しは `heading` に揃える。`title` は、ブラウザのタブの `<title>`（`appName`）と取り違えやすいため。
- 件数の上限は、UX と処理量の2つの観点で決める。
  - 各階層（UX）：グループは2つの配列の合計で10件、グループの設問は30件、設問の項目は20件
  - 項目の総数（処理量）：定義全体で500件
  - 測定では、CPU を4倍遅くした環境で、回答ページのチェック操作の応答が500件で約200ms、\
    1,000件で200ms を超えた（Google の INP の目安は 200ms 以下）。開く時間は1,000件で約3秒。\
    DB は今の Hibernate の設定（1行ごとに連番の取得と INSERT）が最も重いが、500件なら問題にならない。\
    まとめて送る形なら、9,000件でも1秒以内だった。
  - 合計と総数は配列をまたいで数えるので、バックエンドのコードで確かめる。
- 尺度は5段階で固定したままにする。\
  10段階などを許すと、星で表示している UI の意味が薄れるため。\
  後から段階数を変えられるようにする場合は、`survey.json` に任意の段階数（省略時は5）を足す。\
  段階数は回答の意味を変えるので、表示設定ではなく設問の定義に置く必要がある。
- マイグレーションは1つの V1 にまとめ直し、新しいテーブルで始める。段階6で新しい DB に切り替える。\
  旧アプリの回答は、保存期間が5日で、版が変われば無効になるので、引き継ぐ必要がない。\
  配布する管理者は空の DB から始めるので、旧アプリの名前が残る V1〜V3 の履歴は要らない。\
  適用済みのマイグレーションを編集しない決まりがあるため、V1〜V3 を適用済みの DB には使えない。\
  開発環境では、`docker compose down -v` でボリュームを消してから使う。
- スキーマには `$comment` を書かず、`additionalProperties` の意味などの解説は README に書く。\
  スキーマを簡素に保つため。`description` は句点を付けない短い文にする。
- 名前のテンプレートに `{name}` がちょうど1つ、という規則は、スキーマの `pattern` で表す。\
  先読みを使わずに `^[^{}]*\{name\}[^{}]*$` と書けるので、Go の正規表現でも同じ結果になり、エディタでもすぐに分かる。

## 2026-11-06 グループの定義（段階2）

- グループの `id` は `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` にする（英字で始め、ハイフンは末尾や連続では使えない）。\
  ハイフンの規則は、アイコン名の `pattern` と揃える。
- 先頭を英字にするのは、HTML の決まりではない（今の HTML は、空白を含まなければ数字で始めてもよい）。理由は次の3つ。
  - CSS の ID セレクターと `querySelector` は、数字で始まる `id` をエスケープしないと扱えない。\
    今のコードは `getElementById` と属性にしか使っていないので、困る場面はない。
  - 数字だけの `id`（`2024` など）を認めると、`id` をキーにした JavaScript のオブジェクトで順序が並べ替わる。
  - 規則は後から緩めても管理者のファイルはそのまま通るが、後から厳しくすると、更新した時点で起動できなくなる。
- `display.json` の `groupIcons` のキーにも、同じ `pattern` と `patternErrorMessage` を付ける。\
  形の間違いは、起動時の参照の確認でも検出されるが、エディタで先に気づけるようにするため。\
  2つのスキーマに同じ規則を書いているので、変えるときは両方を直す。
- `description` は `selectableGroups` のグループにだけ書ける。グループの定義を2つに分け、共通の部分は `$defs` で共有する。\
  `alwaysShownGroups` では画面に出ないため。`survey.json` の項目は、書き換えると版が変わり、API でブラウザにも届くので、\
  管理者のメモとしても使わない。使われない項目は、定義ファイルに書けるようにしない。
- `selectableGroups` の `description` は任意にする。

## 2026-11-06 画面に出す文字列の中身（段階2）

- 画面に出す文字列の項目は、空欄・先頭と末尾の空白・制御文字を拒否する。\
  各スキーマの `$defs/plainText` に `pattern` を1つ置き、各項目から `$ref` で参照する。\
  `pattern`：`^[^\p{Cc}\p{Zs}]([^\p{Cc}]*[^\p{Cc}\p{Zs}])?$`
- 制御文字を拒否する主な理由は、インジェクションを防ぐこと。\
  定義の文字列は、画面（Vue のバインドだけで `v-html` は使わない）・PDF・CSV（全セルを囲み、数式を無効化）では\
  無害だが、段階4からの起動時のエラー表示とログでは、改行で偽の行を差し込んだり、ESC で端末の表示を操作したりできる。\
  定義ファイルは管理者が書くが、外部から入手したファイルをそのまま使う場合を想定する。
- 先頭と末尾の空白を拒否するのは、空白だけの値が画面で空欄に見えることと、\
  `共通` と `共通 ` のように見た目が同じ値を、文言の重複の確認で見逃さないため。\
  読み込むときに取り除く方法は、ファイルの値と使う値が変わり、空白とみなす文字を3か所で揃える必要があるので採らない。
- 空白と制御文字の範囲は、自分で列挙せず Unicode の一般カテゴリ（`\p{Cc}`：制御文字、`\p{Zs}`：空白）に任せる。\
  `\s` は使わない。JavaScript は全角空白に一致するが、Go は ASCII の空白にしか一致せず、\
  エディタとバックエンドで結果が食い違うため。\
  RFC 9485（I-Regexp）も、`\s` などを除き、Unicode の分類を使えることを求めている。\
  ゼロ幅スペース（U+200B）は書式の文字（`Cf`）なので通るが、通常の入力では入らないので対象外とする。
- すでに `pattern` がある `result.heading` と `csv.fileName` は、その `pattern` に `\p{Cc}` だけを組み込む。\
  `result.heading` は `{name}` を必ず含み、`csv.fileName` は末尾にアプリが `.csv` を付けるので、前後の空白は確かめない。
- `plainText` には `description` を書かない（`$comment` に書く）。\
  `description` があると、VS Code は参照する側ではなく `plainText` の説明を表示するため。\
  各項目には `"type": "string"` も残す。`maxLength` と同じ階層に `type` が無いと、Ajv の strict モードが警告するため。
- 空欄も `pattern` で拒否するので、`plainText` を使う項目からは `minLength: 1` を外した。\
  両方あると、空欄のときにエラーが2つ出るため。
- バックエンドのエラーの文に定義の値を入れるときは、制御文字を `\n` や `\u001b` のような見える表記に置き換える。\
  スキーマで拒否した値そのものをエラー表示に出さないため。置き換えは、エラーの文を組み立てる1か所で行う。

## 2026-11-07 文言の重複（段階2）

- 次の3つの重複を、定義のエラーにする。\
  `ValidationError.vue` はエラーを `グループの名前|設問の見出し` でまとめるので、重複すると別の設問のエラーが1つになるため。\
  CSV でも、同じ名前のグループや設問を見分けられない。
  - グループの名前：2つの配列をまたいで（バックエンドのコード）
  - 設問の見出し：同じグループの中で（バックエンドのコード）
  - 項目の文言：同じ設問の中で（スキーマの `uniqueItems`）
- 項目の文言だけスキーマで確かめるのは、文字列の配列なので `uniqueItems` で表せ、エディタで先に気づけるため。\
  グループの名前と設問の見出しは、配列をまたぐか、オブジェクトの一部の値を比べるので、スキーマでは表せない。\
  VS Code のメッセージは英語（`Array has duplicate items.`）で、配列全体に付き、文言は変えられない。\
  起動時のエラーの文は、ライブラリが返す重複の位置から、バックエンドが日本語で組み立てる。
- 比べ方は、文字列が完全に一致するかどうか。大文字と小文字、全角と半角は区別する。\
  理由は次の3つ。
  - 区別しない比べ方は、Java（`toLowerCase(Locale.ROOT)`）と Go（`strings.ToLower`）で結果が食い違う文字がある\
    （`İstanbul` と `istanbul` は Java では別、Go では重複。`Σίσυφος` と `ΣΊΣΥΦΟΣ` はその逆）。
  - `uniqueItems` は完全に一致するものだけを重複とみなすので、区別しないとエディタと起動時の判定が変わる。
  - `ValidationError.vue` のキーと CSV は、完全に一致しなければ見分けられるので、この比べ方で足りる。
- コードで確かめる2つは、値ごとに出てくる場所を集め、2か所以上あるものを、すべての場所と一緒にエラーにする。\
  先頭と末尾の空白はスキーマで拒否しているので、見た目と判定が揃う。

## 2026-11-07 JSON のキーの重複（段階2）

- 同じオブジェクトの中で同じキーを2回書いた定義ファイルは、バックエンドが読み込むときにエラーにする。\
  JSON の仕様は重複の扱いを決めておらず、多くのライブラリは後の値を黙って使うので、管理者が書き間違いに気づけないため。\
  読み込んだ後のデータには後の値しか残らないので、スキーマやコードの規則では確かめられない。\
  VS Code は黄色の警告（`Duplicate object key`）を出すだけ。
- Spring Boot 版：定義ファイル専用の `JsonMapper` で `StreamReadFeature.STRICT_DUPLICATE_DETECTION` を有効にする。\
  Jackson 3 では既定で無効（ソースで確認）。Spring Boot 全体の `ObjectMapper` の設定は変えない。
- Go 版：`encoding/json/v2` で読み込む（既定で重複を拒否する）。\
  v1 の `encoding/json` は既定で後の値を使う（実行して確認）。
- このエラーはデータを組み立てる前に起きるので、場所は行と列で示す（「エラーメッセージの場所」の節）。

## 2026-11-07 定義ファイルの文字コードと BOM（段階2）

- 定義ファイルは UTF-8 だけを受け付ける。先頭の UTF-8 の BOM（`EF BB BF`）は取り除いてから読み、\
  UTF-8 として正しくないファイル（Shift_JIS、UTF-16 など）はエラーにする。
- BOM を取り除くのは、エディタの画面に表示されず、管理者が見分けにくいため。\
  RFC 8259 も、読み込む側は BOM をエラーにせず無視してよいとしている。
- ライブラリに任せず、自分で取り除き、UTF-8 として厳密に読む。理由は次のとおり。
  - Jackson 3 はバイト列から読むと BOM を読み飛ばし、UTF-16 なども自動で判定する（ソースで確認）。\
    Go の `encoding/json` は BOM があると読めず、Shift_JIS は文字化けしたまま読む（実行して確認）。\
    このままでは、同じファイルが Spring Boot 版と Go 版で違う結果になる。
  - Java は BOM を取り除かずに厳密に読むと、先頭に U+FEFF の文字が残る（実行して確認）。
- Spring Boot 版：BOM を取り除いた後、`CharsetDecoder`（`CodingErrorAction.REPORT`）で文字列にし、\
  バイト列ではなく文字列を `JsonMapper` に渡す（Jackson に文字コードを判定させないため）。
- Go 版：`bytes.TrimPrefix` で BOM を取り除き、`utf8.Valid` で確かめてから `encoding/json/v2` で読む。
- 処理の順序は、BOM の除去と文字コードの確認 → JSON として読む（キーの重複の確認を含む）→ スキーマ → コードの規則。

## 2026-11-07 定義ファイルが無いとき（段階2）

- `survey.json` と `display.json` は、どちらも必須にする。無ければ起動を止める。\
  既定値の文言は汎用的なもので、管理者が期待する文言になる可能性は低いため。\
  ファイル名の書き間違いや置き場所の間違いにも、起動した時点で気づける。
- `display.json` の中の項目は、今までどおりすべて任意にする（書いた項目だけが既定値を上書きする）。\
  アプリの更新で項目が増えても、管理者の今のファイルがそのまま使えるようにするため。
- 配布物には、`display.json` のサンプルを入れる。

## 2026-11-07 エラーメッセージの場所（段階2）

- 起動時と検証コマンドのエラーは、場所をキーの並びと名前の両方で示す。

  ```
  alwaysShownGroups[0].questions[2].items（共通スキル ＞ PC・IT基礎スキル）
    項目が21件あります。20件までにしてください。

  selectableGroups[1].label
    空欄や、先頭・末尾の空白、改行・タブなどの制御文字は使えません。
  ```

  名前だけでは、名前そのものが間違っているときや重複しているときに場所を示せず、項目のような細かい位置も分からない。\
  キーの並びだけでは、どのグループや設問の話かがすぐには分からない。
- キーの並びは `a[0].b` の形で書き、番号は0から数える（JSON Pointer と JavaScript に揃える）。\
  グループの `id` とキーの名前には `.` を使えないので、曖昧にならない。
- 名前は、その値が文字列で、その値自体にスキーマのエラーが無いときだけ、その階層の分を括弧に添える。\
  使えない階層は括弧から外すだけにし、代わりの言い方は用意しない。\
  スキーマのエラーで止めるなら、コードの規則の段階では、すべての名前を使える。
- 重複のエラーは、場所を1行に1つずつ並べる。
- JSON として読み込む前のエラー（キーの重複を含む）は、行と列で示す（例：`survey.json の 12行目 5列目`）。\
  キーの並びも取れるなら添える。
- `display.json` は、キーがそのまま読める形（`groupIcons.engineer`）になるので、名前を添えない。\
  `propertyNames` のエラーは、JSON Pointer がキーの名前を指せないため、場所が親のオブジェクト（`groupIcons`）までになることがある。\
  `groupIcons` は数件の小さいオブジェクトなので、それで足りる。
- エラーの表示順は保証しない。厳密に順序を保つ意味が無いため。\
  Spring Boot と Go で共用するテスト用の定義で、期待するエラーを比べるときは、順序によらない比べ方にする。

## 2026-11-07 スキーマの版（段階2）

- JSON Schema は Draft 2020-12 で書く。v1 が公開されたら、移行を検討する（2026-11 の時点では、公開を確認できていない）。
  - draft-07 には下げない。`$defs` と、`$ref` と並べたキーワード（`plainText` を参照する項目の `maxLength`）が使えず、書き直しが要るため。
  - v1 に移行しても、定義ファイルは `$schema` の相対パスでスキーマを参照するだけなので、定義ファイルのバイト列と版は変わらない。
- VS Code は、2019-09 と 2020-12 への対応が限定的とされている（公式の文書）。\
  スキーマで使うキーワードが VS Code で効くかは、スキーマを正式な場所に置いた後に確かめる。
- 2020-12 では、知らないキーワードは無視される。スキーマのキーワードを書き間違えると（`maxLenght` など）、エラーにならず、その規則が効かなくなる。\
  共用するテスト用の定義が規則を1つずつすべて試していれば、期待したエラーが出ないので検出できる。
- グループの定義は、`properties` を各定義に書き、値だけを `$defs` から参照する今の形を保つ。\
  `additionalProperties: false` は同じ階層の `properties` しか見ないので、共通の部分を `allOf` で取り込む形にすると、`id` などが書き間違えたキーとして拒否されるため。\
  取り込んだ分も数える `unevaluatedProperties` は、VS Code でどこまで効くかが分からないので使わない。
- `format` は、2020-12 では既定で検証されない（注釈として扱われる）。今は使っていないが、足すときはエラーにならないことに注意する。

## 2026-11-09 TOP の挙動（段階2）

- グループの件数による TOP の挙動
  - `selectableGroups` が0件：選ぶ欄を出さない。
  - `alwaysShownGroups` が0件：1つ以上選ばないと開始できない。\
    開始ボタンは `aria-disabled` で無効を示す。結果ページの共有ボタン（`ShareButton.vue`）と同じ作りで、`AnimatedIconButton.vue` の `inactive` を使う。
  - 両方0件：定義のエラー（決定済み）。
- TOP には、表示設定に書いたときに出せる看板（操作の説明などを書く）を置く。選ぶ欄の有無にかかわらず出せる。\
  看板か選ぶ欄の、どちらかは必ず表示する。表示設定に看板を書かなかったときの扱いは、実装のときに決める。
- 看板の文章は、段落ごとの文字列の配列で書く。`plainText` で改行を拒否しているため。\
  配列の要素も `plainText` を参照する。画面では段落ごとに `<p>` を並べ、`{{ }}` で表示する（`v-html` を使わない）。\
  リンクや Markdown には対応しない。必要になったら、`https:` だけを許す形などを、その時点で設計する。
- 回答ページ（`/survey`）にガードを入れ、表示するグループが無いときは TOP へ移す。TOP を経由する動線も整える。\
  判定は「TOP から来たか」ではなく「表示するグループがあるか」で行う。\
  選んだ状態はブラウザに残るので、再訪問した利用者が、TOP を通らずに続きから回答できる今の動きを保つため。
- 文字の向きを入れ替える文字（U+202E など）を含む書式の文字（`Cf`）は、`plainText` で拒否しない。\
  故意でなければ入らないため。

## 2026-11-09 グループの並び順（段階2）

  回答ページ・結果ページ・CSV・PDF のすべてで同じ順序にする。TOP のカードも定義の順にする。

## 2026-11-09 定義ファイルの置き場所（段階2）

- JSON Schema は `schema/`、設問の定義と表示設定は `surveys/<名前>/` に置く。どちらもリポジトリ直下に置き、ソースコードとは分ける。\
  1つのアンケートに関わるファイル（`survey.json`・`display.json`・管理者が用意するアイコン）は、1つのフォルダにまとめる。
- 配布物でも、`schema/` と `surveys/` を同じ位置関係で使う。\
  管理者は、サンプルのフォルダを `surveys/` の中に複製して書き始める。\
  どのフォルダも同じ深さなので、`$schema`（`../../schema/survey.schema.json`）を書き直さずに済む。
- バックエンドは、環境変数（例：`SURVEY_DIR`）で指定したフォルダを読む。\
  開発中も、サンプルやテスト用の定義の切り替えに使える。
- 配布の形のイメージ（細かい構成は段階7・8で決める）

  ```
  コンテナイメージ
  /app/
  ├── survey-sheet      Go のバイナリ（schema/ を埋め込む）
  ├── web/              vue-frontend のビルド結果
  └── surveys/          管理者のフォルダをマウントする

  管理者が受け取る設定ファイル一式（ソースコードは含まない）
  survey-sheet/
  ├── compose.yaml
  ├── .env.example      SURVEY_DIR、PDF 用の AWS など
  ├── schema/           エディタのためだけに同梱する
  └── surveys/
      ├── skill-sheet/  サンプル
      └── my-survey/    管理者がサンプルを複製して作る
  ```

- 起動時の検証は、バイナリに埋め込んだスキーマで行う。設定ファイル一式の `schema/` は、エディタのための写し。\
  管理者がイメージだけを新しい版に上げると、エディタと起動時の判定が食い違うことがある（起動時の判定が正）。\
  リリースごとに、イメージの版と設定ファイル一式を組にして配る形を、段階8で検討する。
- 2つ目のサンプルのテーマは、機能の改修が終わってから、そのときの仕様に合うものを選ぶ。\
  先に決めると、仕様が変わったときに合わないテーマになる可能性があるため。
