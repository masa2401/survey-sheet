# 決定事項

方針に関わる決定の、現在の内容をまとめる。
日常の作業で守るルールは `.claude/rules/` にある。

## リポジトリと配布

- 旧リポジトリ（CreateSkillSheet）から新しいリポジトリ（survey-sheet）に切り出し、コミット履歴を引き継いだ
- 配布するのは、バックエンドを Go で実装した版。Spring Boot 版は配布しない
- Go への置き換えは、アプリの大枠を Spring Boot 版で完成させた後に行う
- 配布用の整備（ROADMAP の段階8）は、Go に置き換えた後に行う
- 配信は同一デプロイを既定にする
- 設問の差し替えは、管理者が定義ファイルを編集して再起動する形。画面からの編集機能と認証は持たない
- 設問を差し替えたら、以前の回答は使えなくする
- 回答そのものを URL に入れるクエリ方式の共有（`#/result?data=`）は削除する
- Node と Java のバージョンは `.nvmrc` と `.java-version` で指定し、CI も同じファイルを参照する
- `deploy.yml` は手動実行のみ
- `DESIGN_NOTES.md` は削除する
- `README.md` は、利用者が自分の環境に構築するための手順書にする

## 画面の言語

- 日本語の固定の文言で実装する
- 英語版は、配布の段階で別の版として配布する。英語以外の言語は当面対応しない
- 1つのインスタンスの中で言語を切り替える仕組みは作らない
- 英語版の文面は、尺度の名前を差し込む文でも、冠詞の要らない言い回しにする

## 設定ファイルの構成

- 設問の定義（`survey.json`）と表示設定（`display.json`）に分ける
  - 回答の意味が変わるものを設問の定義に、変わらないものを表示設定に置く
  - 版のハッシュは、設問の定義だけで計算する
- 形式は JSON。手で書きにくいという問題が出たら、YAML への対応を検討する
- 2つのファイルは、どちらも必須。無ければ起動を止める
- 配布物に `display.json` のサンプルを入れる
- 置き場所
  - JSON Schema は `schema/`、設問の定義と表示設定は `surveys/<名前>/`（どちらもリポジトリ直下）
  - 1つのアンケートのファイル（`survey.json`・`display.json`・管理者が用意するアイコン）は、1つのフォルダにまとめる
  - 配布物でも同じ位置関係にする。管理者は、サンプルのフォルダを `surveys/` の中に複製して書き始める
  - バックエンドは、環境変数（例：`SURVEY_DIR`）で指定したフォルダを読む
- 配布の形のイメージ（細かい構成は段階7・8で決める）

  ```
  コンテナイメージ
  /app/
  ├── survey-sheet      Go のバイナリ（schema/ を埋め込む）
  ├── web/              vue-frontend のビルド結果
  └── surveys/          管理者のフォルダをマウントする

  管理者が受け取る設定ファイル一式（ソースコードは含まない）
  survey-sheet/
  ├── compose.yaml
  ├── .env.example      SURVEY_DIR、PDF 用の AWS など
  ├── schema/           エディタのためだけに同梱する
  └── surveys/
      ├── skill-sheet/  サンプル
      └── my-survey/    管理者がサンプルを複製して作る
  ```

- 起動時の検証は、バイナリに埋め込んだスキーマで行う。設定ファイル一式の `schema/` はエディタ用の写しで、食い違ったときは起動時の判定が正
- 2つ目のサンプル定義のテーマは、機能の改修が終わってから選ぶ

## 設問の定義（`survey.json`）

- 階層の名前は `groups`（グループ）→ `questions`（設問）→ `items`（項目）
- グループの配列は `alwaysShownGroups`（全員が回答する）と `selectableGroups`（TOP で選んだときだけ出す）
- グループの名前は `label`、設問の見出しは `title`
- 名前の変更は、まず JSON だけに行い、読み込むときに今の型に変換する
  - コード（型・テスト・e2e のロケーター `data-slot="category-card"` など）と DB の名前は、段階3と段階4で置き換える
  - 置き換えは、作業のたびに範囲を確認してから進める
- グループの `id`
  - 管理者が文字列で書く（例：`engineer`）。HTML の `id` 属性にも使う
  - `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`（ハイフンの規則はアイコン名の `pattern` と揃える）
  - 2つの配列をまたいで重複させない
- 設問と項目には `id` を書かない
  - アプリが配列の順序から番号を振る（1始まり、親の中で振り直す）
  - DB には振った番号を integer で保存する。テーブルの構造は変えない
- 番号を振るものは、必ず配列で書く
- 番号はバックエンドが振り、定義の API で渡す。フロントでは振らない
- 画面に出ない項目は、定義ファイルに書けるようにしない（管理者のメモ用の項目も持たない）
- `description` は、`selectableGroups` のグループにだけ任意で書ける
  - グループの定義を2つに分け、共通の部分は `$defs` で共有する
- 件数の上限
  - グループ：2つの配列の合計で10件
  - グループの設問：30件
  - 設問の項目：20件
  - 項目の総数：定義全体で500件
  - 合計と総数は、バックエンドのコードで確かめる
- グループの件数の規則（どちらもバックエンドのコードで確かめる）
  - 両方0件：定義のエラー
  - `alwaysShownGroups` が0件で `selectableGroups` が1件：定義のエラー
- 並び順は `alwaysShownGroups` → `selectableGroups`、それぞれ定義の順
  - 回答ページ・結果ページ・CSV・PDF・TOP のカードで揃える
  - 選べるグループを先に出す並べ方は無い。必要になったら、並び順の項目を足す
- 文言の重複を定義のエラーにする
  - グループの名前：2つの配列をまたいで（バックエンドのコード）
  - 設問の見出し：同じグループの中で（バックエンドのコード）
  - 項目の文言：同じ設問の中で（スキーマの `uniqueItems`）
  - 比べ方は完全一致。大文字と小文字、全角と半角は区別する
  - コードで確かめる2つは、重複する値のすべての場所をエラーにする
- 尺度は5段階で固定する
  - 段階数を変えられるようにする場合は、`survey.json` に任意の段階数（省略時は5）を足す
- 回答は1〜5の数値で保存する。バックエンドは範囲だけを確かめる

## 表示設定（`display.json`）

- ビルド時ではなく、画面を開いたときに読み込む
- 項目はすべて任意。書いた項目だけが既定値を上書きする（オブジェクトはキーごと、配列は丸ごと置き換える）
- 複数の画面で使うもの（`appName`・`scale`・`groupIcons`）と、画面ごとのもの（`top`・`result`・`csv`）に分ける
- 見出しのキーは `heading` に揃える
- 項目と既定値

  | 項目              | 内容                                              | 既定値                                 |
  | ----------------- | ------------------------------------------------- | -------------------------------------- |
  | `appName`         | アプリ名（ヘッダーとブラウザのタブ）              | アンケート                             |
  | `scale.name`      | 尺度の名前                                        | 評価                                   |
  | `scale.levels`    | 5段階それぞれの説明                               | 低い／やや低い／ふつう／やや高い／高い |
  | `groupIcons`      | グループの `id` とアイコンの対応                  | なし                                   |
  | `top.banner`      | TOP の看板（段落ごとの文字列の配列）              | なし                                   |
  | `top.heading`     | グループを選ぶ欄の見出し                          | 件数で切り替える（「TOP」の節）        |
  | `result.heading`  | 結果ページの見出し（`{name}` をちょうど1つ含む）  | `{name}のアンケート`                   |
  | `csv.fileName`    | CSV のファイル名（`{name}` と `{date}` を使える） | `{name}_アンケート_{date}`             |
  | `csv.itemHeading` | CSV の表の項目の列の見出し                        | 評価項目                               |

- アイコン
  - 指定の無いグループには表示しない
  - Lucide の名前か、管理者が用意した SVG（`custom/` で始まる名前）を指定する
  - SVG ファイルを配信し、CSS のマスクで文字色の単色として表示する（`@lucide/vue` を名前で動的に読み込まない）
  - `custom/` の SVG はフォルダから配信し、起動時にファイルがあるかを確かめる。起動後に消された場合は、アイコンが出なくなるだけ
  - `groupIcons` のキーには、グループの `id` と同じ `pattern` と `patternErrorMessage` を付ける（2つのスキーマで揃える）

## 定義の API

- 設問の定義・表示設定・版を、1本の API でまとめて返す。必要になったら分ける
- フロントは、画面を開いたときにこの API を読む
- 応答の形

  ```json
  {
    "version": "…",
    "survey": {
      "groups": [
        {
          "id": "common",
          "label": "共通スキル",
          "questions": [
            {
              "id": 1,
              "title": "コミュニケーションツール",
              "prompt": "…",
              "items": [
                { "id": 1, "label": "Slack" },
                { "id": 2, "label": "Microsoft Teams" }
              ]
            }
          ]
        }
      ]
    },
    "display": { … }
  }
  ```

- `version`：版のハッシュ
- `survey.groups`：`alwaysShownGroups` → `selectableGroups` の順で1つの配列にまとめ、全員が回答するグループかの印を付ける
  - まとめる処理は、バックエンドの起動時に行う
  - `description` は、選べるグループにだけ入る
- 設問と項目は、バックエンドが振った番号を `id` に持つ。項目は `{ "id", "label" }` のオブジェクトにする
- `display`：`display.json` を書いたまま返す
- 定義と回答の結合（文言の解決）はフロントで行う。シートの API は、番号と回答の値だけを扱う

## 画面の固定の文言

- テンプレートに直接書かず、文面の一覧（`src/data/texts.ts`）にまとめる
- 表示設定の値の差し込みと既定値の適用は、`composables/useTexts.ts` で行う
- vue-i18n などのライブラリは入れない
- 対象は、画面に出る文字と `aria-label`。`console` のログと、画面に出ない `Error` の文は対象外
- 表示設定のアイコン（`groupIcons`）は扱わない。渡し方と配信は、定義の API と一緒に決める
- `csvUtils.ts` は Vue に依存しない関数のまま、完成したファイル名や見出しを引数で受け取る
- 差し込むのは尺度の名前（`scale.name`）
- 常体を基本にする。「〜してください」「お探しの」「お試しください」は今のまま
- 回答者の名前の入力は必須。呼び名は固定で「名前」
- 変える文面
  - 共有ビューのボタン：「自分もアンケートに答える」（固定）
  - リンク切れの文：「お探しのアンケートは存在しないか、削除された可能性があります。」
  - 名前の入力欄：「名前を入力」
  - 名前のラベル：「名前（20文字まで）」
  - 印刷・共有ボタンの案内：「名前を入力すると、印刷・共有機能が利用できます」
  - CSV の1行目の見出し：「名前」
- 変えない文面
  - 「名前を編集する」「アンケートを開始」
  - CSV の「カテゴリ」「質問項目」
  - 回答ページの案内とエラーの「項目」
  - 名前が空のときの `Guest`

## TOP

- グループの件数による選ぶ欄の見出し（既定値）と補足（固定）

  | 全員が回答するグループ | 選べるグループ | 見出し                                         | 補足                                         |
  | ---------------------- | -------------- | ---------------------------------------------- | -------------------------------------------- |
  | 1件以上                | 2件以上        | 該当するカテゴリを選択してください(複数選択可) | 選択しない場合は、共通の質問のみ表示されます |
  | 1件以上                | 1件            | 該当するカテゴリを選択してください             | 同上                                         |
  | 0件                    | 2件以上        | 該当するカテゴリを選択してください(複数選択可) | 出さない                                     |
  | 問わない               | 0件            | 選ぶ欄ごと出さない                             | 出さない                                     |

- 管理者が `top.heading` を書いた場合は、件数によらずその文を使う
- 全員が回答するグループが0件のとき、1つ以上選ぶまで開始ボタンを無効にする
  - `aria-disabled` で示す（`AnimatedIconButton.vue` の `inactive`）
  - `ShareButton.vue` の名前が未入力のときと同じ作り
  - ツールチップ：「1つ以上選択すると開始できます」
  - 押したときは、1枚目のカードへフォーカスを移す
- 看板（`top.banner`）
  - 1〜5段落、1段落40字まで。見出しは持たない
  - 選ぶ欄の有無にかかわらず出せる
  - 看板か選ぶ欄の、どちらかは必ず表示する。看板を書かなかったときの扱いは、実装のときに決める
  - 段落ごとに `<p>` を並べ、`{{ }}` で表示する
  - リンクと Markdown には対応しない。必要になったら、その時点で設計する
- 回答ページ（`/survey`）に、表示するグループが無いときは TOP へ移すガードを入れる。TOP を経由する動線も整える
  - 判定は「表示するグループがあるか」で行う（「TOP から来たか」ではない）

## 定義ファイルの検証

- 対象は、管理者が定義ファイルを編集するときの書き間違い。配布する完成形（Go 版）を前提に決める
- 段階4より前は、エディタでスキーマが効けば足りる
- 検証は、エディタ（JSON Schema）・コミット時のテスト・起動時の3段で行い、同じ規則を使う
- 形は JSON Schema、スキーマで表せない規則はバックエンドのコードで確かめる
  - コードは検証処理の1か所に置き、起動時・検証コマンド・CI のテストから同じ処理を呼ぶ
- フロントは、起動時の検証を通った定義だけを受け取る前提にし、検証しない
- バックエンドは起動時に `display.json` も検証し、正しければそのままフロントに返す。変更は再起動で反映する
- 間違いが1つでもあれば、起動を止める
- 処理の順序：BOM の除去と文字コードの確認 → JSON として読む（キーの重複の確認を含む）→ スキーマ → コードの規則
- 文字コード
  - UTF-8 だけを受け付ける。先頭の UTF-8 の BOM（`EF BB BF`）は取り除く。UTF-8 として正しくないファイルはエラーにする
  - ライブラリに文字コードを判定させず、自分で処理する
  - Spring Boot 版：BOM を取り除き、`CharsetDecoder`（`CodingErrorAction.REPORT`）で文字列にしてから `JsonMapper` に渡す
  - Go 版：`bytes.TrimPrefix` で BOM を取り除き、`utf8.Valid` で確かめてから `encoding/json/v2` で読む
- 同じオブジェクトの中のキーの重複は、読み込むときにエラーにする
  - Spring Boot 版：定義ファイル専用の `JsonMapper` で `StreamReadFeature.STRICT_DUPLICATE_DETECTION` を有効にする（Spring Boot 全体の `ObjectMapper` は変えない）
  - Go 版：`encoding/json/v2` で読む
- 画面に出す文字列（`plainText`）
  - 空欄・先頭と末尾の空白・制御文字を拒否する
  - 各スキーマの `$defs/plainText` に `pattern` を置き、各項目から `$ref` で参照する
  - `pattern`：`^[^\p{Cc}\p{Zs}]([^\p{Cc}]*[^\p{Cc}\p{Zs}])?$`
  - `\s` は使わず、Unicode の一般カテゴリ（`\p{Cc}`・`\p{Zs}`）を使う
  - 書式の文字（`Cf`。U+200B、U+202E など）は拒否しない
  - `result.heading` と `csv.fileName` は、それぞれの `pattern` に `\p{Cc}` だけを組み込む
  - `plainText` を参照する項目には `minLength: 1` を付けない
- `pattern` を使う項目には、`patternErrorMessage` を付ける
- `pattern` の正規表現は、先読み（`(?=...)`）などを使わない書き方にする

## エラーメッセージ

- 起動時と検証コマンドのエラーは、日本語で組み立てる。検証ライブラリが返す違反の種類と値から文を作る
- 場所は、キーの並びと名前の両方で示す

  ```
  alwaysShownGroups[0].questions[2].items（共通スキル ＞ PC・IT基礎スキル）
    項目が21件あります。20件までにしてください。

  selectableGroups[1].label
    空欄や、先頭・末尾の空白、改行・タブなどの制御文字は使えません。
  ```

- キーの並びは `a[0].b` の形で書き、番号は0から数える
- 名前は、その値が文字列で、その値自体にスキーマのエラーが無いときだけ、その階層の分を括弧に添える。使えない階層は括弧から外す
- 重複のエラーは、場所を1行に1つずつ並べる
- JSON として読み込む前のエラー（キーの重複を含む）は、行と列で示す（例：`survey.json の 12行目 5列目`）。キーの並びも取れるなら添える
- `display.json` のエラーには名前を添えない。`propertyNames` のエラーの場所は、親のオブジェクトまでになってよい
- エラーの表示順は保証しない。共用するテスト用の定義で期待するエラーを比べるときは、順序によらない比べ方にする
- 定義の値をエラーの文に入れるときは、制御文字を `\n` や `\u001b` のような見える表記に置き換える。置き換えは、エラーの文を組み立てる1か所で行う

## JSON Schema の書き方

- Draft 2020-12 で書く。draft-07 には下げない
- v1 が公開されたら移行を検討する。移行するときは、`patternErrorMessage` が使えるかを確かめ直す
- 定義ファイルの `$schema` は相対パスで書き、スキーマのファイルを配布物に同梱する
- `$comment` は書かない（`plainText` の説明だけは `$comment` に書く）。解説は README に書く
- `description` は、句点を付けない短い文にする。`plainText` には書かない
- `plainText` を参照する項目にも、`"type": "string"` を書く
- グループの定義は、`properties` を各定義に書き、値だけを `$defs` から参照する。`allOf` での取り込みと `unevaluatedProperties` は使わない
- `format` は既定で検証されない。足すときは、エラーにならないことに注意する
- `result.heading` の `{name}` がちょうど1つという規則は、`pattern`（`^[^{}]*\{name\}[^{}]*$`）で表す

## DB とデータ

- マイグレーションは1つの V1 にまとめ直し、新しいテーブルで始める
  - 段階6で新しい DB に切り替える。旧アプリの回答は引き継がない
  - 開発環境では、`docker compose down -v` でボリュームを消してから使う
- `shareToken` は使っていない。扱いは段階4で決める
- `AnswerDto.value` に `@NotNull` を付ける（段階4で DTO を作り直すとき）

## CI

- ブランチ保護の必須チェックは、集約ジョブ `ci-result` に一本化している

## 依存関係

- Dependabot は alerts と security updates だけを使い、npm の version updates は使わない
- `vue-frontend` では `npm audit fix` を使わず、脆弱性のあるパッケージを個別に更新する
- 開発用の依存にしか無く、外部からの入力が届かない脆弱性は、上流の更新を待つ

## PDF 生成

- 生成のきっかけは PDF ボタンの押下。名前を確定したときの保存による事前生成は、待ち時間を短くするためのもの
- PDF が無いときに生成を依頼する経路は `regenerate`。生成に失敗したときの作り直しにも使う
- 生成失敗の区別は、バックエンドのトラブルシューティング用。利用者には通知しない。恒久的な失敗は、デプロイ時に確認する
- S3 のライフサイクルルールの日数は、シートの保存日数（5日）と揃える

## README 用の動画

- 作業ブランチにはコミットせず、メディア専用のブランチに置いて、`raw.githubusercontent.com` から参照する
- 形式はアニメーション WebP。ライトとダークの両方を撮影し、`<picture>` で切り替える
- 容量の目安は 5MB 以下、表示幅は 720px
