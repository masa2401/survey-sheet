# 決定事項

方針に関わる決定の、現在の内容をまとめる。
日常の作業で守るルールは `.claude/rules/` にある。

## リポジトリと配布

- 旧リポジトリ（CreateSkillSheet）から新しいリポジトリ（survey-sheet）に切り出し、コミット履歴を引き継いだ
- 配布するのは、バックエンドを Go で実装した版。Spring Boot 版は配布しない
- Go への置き換えは、アプリの大枠を Spring Boot 版で完成させた後に行う
- 配布用の整備（ROADMAP の段階8）は、Go に置き換えた後に行う
- 配信は同一デプロイを既定にする
- Spring Boot 版の公開デプロイは、フロントを別にデプロイする
- 旧アプリ（公開中のスキルシート作成アプリ）とは、デプロイを分ける。同じオリジンで共存させない
- 設問の差し替えは、管理者が定義ファイルを編集して再起動する形
  - 最小構成では、画面からの編集機能と認証は持たない。形になってから、管理画面の追加を検討する
- 設問を差し替えたら、ブラウザに残った入力途中の状態は、名前を含めて使えなくする。保存済みのシートは、期限まで回答したときの文言で表示する
- 回答そのものを URL に入れるクエリ方式の共有（`#/result?data=`）は削除する
- Node と Java のバージョンは `.nvmrc` と `.java-version` で指定し、CI も同じファイルを参照する
- `deploy.yml` は手動実行のみ
- `README.md` は、利用者が自分の環境に構築するための手順書にする

## 画面の言語

- 日本語の固定の文言で実装する
- 英語版は、配布の段階で別の版として配布する。英語以外の言語は当面対応しない
- 1つのインスタンスの中で言語を切り替える仕組みは作らない
- 英語版の文面は、尺度の名前を差し込む文でも、冠詞の要らない言い回しにする

## 設定ファイルの構成

- 設問の定義（`survey.json`）と表示設定（`display.json`）に分ける
  - 回答の意味が変わるものを設問の定義に、変わらないものを表示設定に置く
  - 版のハッシュは、設問の定義だけで計算する
- 形式は JSON。手で書きにくいという問題が出たら、YAML への対応を検討する
- 2つのファイルは、どちらも必須。無ければ起動を止める
- 配布物に `display.json` のサンプルを入れる
- 置き場所
  - JSON Schema は `schema/`、設問の定義と表示設定は `surveys/<名前>/`（どちらもリポジトリ直下）
  - 1つのアンケートのファイル（`survey.json`・`display.json`・管理者が用意するアイコン）は、1つのフォルダにまとめる
  - 配布物でも同じ位置関係にする。管理者は、サンプルのフォルダを `surveys/` の中に複製して書き始める
  - バックエンドは、環境変数（例：`SURVEY_DIR`）で指定したフォルダを読む
- 配布の形のイメージ（細かい構成は段階7・8で決める）

  ```
  コンテナイメージ
  /app/
  ├── survey-sheet      Go のバイナリ（schema/ を埋め込む）
  ├── web/              vue-frontend のビルド結果
  └── surveys/          管理者のフォルダをマウントする

  管理者が受け取る設定ファイル一式（ソースコードは含まない）
  survey-sheet/
  ├── compose.yaml
  ├── .env.example      SURVEY_DIR など
  ├── schema/           エディタのためだけに同梱する
  └── surveys/
      ├── skill-sheet/  サンプル
      └── my-survey/    管理者がサンプルを複製して作る
  ```

- 起動時の検証は、バイナリに埋め込んだスキーマで行う。設定ファイル一式の `schema/` はエディタ用の写しで、食い違ったときは起動時の判定が正
- 2つ目のサンプル定義のテーマは、機能の改修が終わってから選ぶ

## 設問の定義（`survey.json`）

- 階層の名前は `groups`（グループ）→ `questions`（設問）→ `items`（項目）
- グループの配列は `alwaysShownGroups`（全員が回答する）と `selectableGroups`（TOP で選んだときだけ出す）
- グループの名前は `label`、設問の見出しは `title`
- コード（型・テスト・e2e のロケーター `data-slot="category-card"` など）と DB の名前は、定義の名前に置き換える
- グループの `id`
  - 管理者が文字列で書く（例：`engineer`）。HTML の `id` 属性にも使う
  - `^[a-z][a-z0-9]*(-[a-z0-9]+)*$`（ハイフンの規則はアイコン名の `pattern` と揃える）
  - 2つの配列をまたいで重複させない
- 設問と項目には `id` を書かない
  - アプリが配列の順序から番号を振る（1始まり、親の中で振り直す）
- 番号を振るものは、必ず配列で書く
- 番号はバックエンドが振り、定義の API で渡す。フロントでは振らない
- 画面に出ない項目は、定義ファイルに書けるようにしない（管理者のメモ用の項目も持たない）
- `description` は、`selectableGroups` のグループにだけ任意で書ける
  - グループの定義を2つに分け、共通の部分は `$defs` で共有する
- 件数の上限
  - グループ：2つの配列の合計で10件
  - グループの設問：30件
  - 設問の項目：20件
  - 項目の総数：定義全体で500件
  - 合計と総数は、バックエンドのコードで確かめる
- グループの件数の規則（どちらもバックエンドのコードで確かめる）
  - 両方0件：定義のエラー
  - `alwaysShownGroups` が0件で `selectableGroups` が1件：定義のエラー
- 並び順は `alwaysShownGroups` → `selectableGroups`、それぞれ定義の順
  - 回答ページ・結果ページ・CSV・PDF・TOP のカードで揃える
  - 選べるグループを先に出す並べ方は無い。必要になったら、並び順の項目を足す
- 文言の重複を定義のエラーにする
  - グループの名前：2つの配列をまたいで（バックエンドのコード）
  - 設問の見出し：同じグループの中で（バックエンドのコード）
  - 項目の文言：同じ設問の中で（スキーマの `uniqueItems`）
  - 比べ方は完全一致。大文字と小文字、全角と半角は区別する
  - コードで確かめる2つは、重複する値のすべての場所をエラーにする
- 尺度は5段階で固定する
  - 段階数を変えられるようにする場合は、`survey.json` に任意の段階数（省略時は5）を足す
- 回答は1〜5の数値

## 表示設定（`display.json`）

- ビルド時ではなく、画面を開いたときに読み込む
- 項目はすべて任意。書いた項目だけが既定値を上書きする（オブジェクトはキーごと、配列は丸ごと置き換える）
- 既定値は、バックエンドのコードに持ち、起動時の検証の後に当ててメモリに持つ
  - Spring Boot 版は Java の定数、Go 版は構造体の値で書く
  - `top.heading` の既定値は、起動時にグループの件数から決める（「TOP」の表）
- 複数の画面で使うもの（`appName`・`scale`・`groupIcons`）と、画面ごとのもの（`top`・`result`・`csv`）に分ける
- 見出しのキーは `heading` に揃える
- 項目と既定値

  | 項目              | 内容                                              | 既定値                                 |
  | ----------------- | ------------------------------------------------- | -------------------------------------- |
  | `appName`         | アプリ名（ヘッダーとブラウザのタブ）              | アンケート                             |
  | `scale.name`      | 尺度の名前                                        | 評価                                   |
  | `scale.levels`    | 5段階それぞれの説明                               | 低い／やや低い／ふつう／やや高い／高い |
  | `groupIcons`      | グループの `id` とアイコンの対応                  | なし                                   |
  | `top.banner`      | TOP の看板（段落ごとの文字列の配列）              | なし                                   |
  | `top.heading`     | グループを選ぶ欄の見出し                          | 件数で切り替える（「TOP」の節）        |
  | `result.heading`  | 結果ページの見出し（`{name}` をちょうど1つ含む）  | `{name}のアンケート`                   |
  | `csv.fileName`    | CSV のファイル名（`{name}` と `{date}` を使える） | `{name}_アンケート_{date}`             |
  | `csv.itemHeading` | CSV の表の項目の列の見出し                        | 評価項目                               |

- アイコン
  - 指定の無いグループには表示しない
  - Lucide の名前か、管理者が用意した SVG（`custom/` で始まる名前）を指定する
  - SVG ファイルを配信し、CSS のマスクで文字色の単色として表示する（`@lucide/vue` を名前で動的に読み込まない）
  - `custom/` の SVG はフォルダから配信する。ファイルが無くても起動は止めず、アイコンが出なくなるだけにする
  - `groupIcons` のキーには、グループの `id` と同じ `pattern` と `patternErrorMessage` を付ける（2つのスキーマで揃える）

## 定義の API

- 設問の定義・表示設定・版を、1本の API でまとめて返す。必要になったら分ける
- フロントは、画面を開いたときにこの API を読む
- 応答の形

  ```json
  {
    "version": "…",
    "survey": {
      "groups": [
        {
          "id": "common",
          "label": "共通スキル",
          "questions": [
            {
              "id": 1,
              "title": "コミュニケーションツール",
              "prompt": "…",
              "items": [
                { "id": 1, "label": "Slack" },
                { "id": 2, "label": "Microsoft Teams" }
              ]
            }
          ]
        }
      ]
    },
    "display": { … }
  }
  ```

- `version`：版のハッシュ
- `survey.groups`：`alwaysShownGroups` → `selectableGroups` の順で1つの配列にまとめ、全員が回答するグループかの印を付ける
  - まとめる処理は、バックエンドの起動時に行う
  - `description` は、選べるグループにだけ入る
- 設問と項目は、バックエンドが振った番号を `id` に持つ。項目は `{ "id", "label" }` のオブジェクトにする
- `display`：`display.json` に既定値を当てた結果を返す。すべての項目が埋まった形になる
  - フロントが使わない `csv.*` も含める

## シートの API

- API の一覧（パスは実装のときに決める）

  | API      | リクエスト               | 応答                         |
  | -------- | ------------------------ | ---------------------------- |
  | 組み立て | 版・回答                 | 文言つきの回答。保存はしない |
  | URL 共有 | 冪等キー・版・名前・回答 | ID と共有 URL                |
  | PDF 生成 | 冪等キー・版・名前・回答 | 202。ID とダウンロードの URL |
  | CSV      | 冪等キー・版・名前・回答 | ID とダウンロードの URL      |
  | 読み出し | シートの ID              | 名前と文言つきの回答         |

- URL 共有・PDF 生成・CSV は、同じ保存の処理を通してから、それぞれの操作を行う
- 保存したシートを変える操作は持たない
- リクエストの形
  - 番号・値・版を送り、文言は送らない
  - JSON のキーは定義の API に揃える
  - 組み立ては、下の形から `idempotencyKey` と `userName` を除いたもの
  - 冪等キーの項目の名前は、実装のときに決める

  ```json
  {
    "idempotencyKey": "…",
    "version": "…",
    "userName": "…",
    "groups": [
      {
        "id": "common",
        "questions": [{ "id": 1, "items": [{ "id": 1, "value": 4 }] }]
      }
    ]
  }
  ```

- 応答の形

  ```jsonc
  // URL 共有
  { "id": "…", "shareUrl": "https://…/#/result?id=…" }

  // PDF 生成・CSV
  { "id": "…", "downloadUrl": "https://…" }
  ```

  - 新しく保存したときと、同じ冪等キーのシートを返したときで、本文は同じにする
  - 共有 URL とダウンロードの URL は、バックエンドが組み立てる

- グループは、定義の文字列の `id` で識別する
- 版の確認と定義との照合は、組み立てと保存で同じ1つの処理を使う（Spring Boot 版は service の1つのメソッド、Go 版はハンドラーから呼ぶ1つの関数）
  - 今の版と違えば断る。比べるのは、フロントが送った版とメモリの版
- 入力の検証
  - 型・必須・値の範囲（1〜5）・件数は、入れ物の検証で行う（Spring Boot 版は DTO の Bean Validation）
  - DTO の件数の上限は、定義の上限に合わせる（グループ10・設問30・項目20）
  - 次のものは、リクエストの誤りとして断る
    - 定義に無いグループの `id`、設問の番号、項目の番号
    - 同じグループ・設問・項目の重複
    - 項目が1つも無い
- 名前の検証
  - 空欄不可、20文字まで（フロントの `NAME_MAX_LENGTH` と揃える）
  - 文字数は UTF-16 の単位で数える。Spring Boot 版は `@Size`、Go 版は `unicode/utf16` で数える
  - 先頭の文字（`=` `+` `-` `@`）の確認は行わない
- 冪等キー
  - フロントが作る UUID。リクエストの本文に入れる
  - 同じ冪等キーで期限内のシートがあれば、新しく保存せずにそのシートを使う。無ければ保存する
  - 同じ冪等キーの期限切れの行が残っていれば、同じトランザクションの中で消してから保存する
  - 同じ冪等キーで、名前か文言つきの回答が保存したシートと違えば 422 を返し、バックエンドのログに警告を出す
  - 同時に届いた同じ冪等キーのリクエストは、一意の制約で1行にまとめる（`INSERT … ON CONFLICT DO NOTHING` の後に読む）
- 保存は、バックエンドがメモリの定義から文言を引いて文言つきの回答を組み立て、1行で保存する
- 読み出しは、保存した文言つきの回答を返す。版は比べない
- シートの有無と期限の確認は1つの処理にまとめ、共有ビュー・PDF の `/status`・PDF と CSV のダウンロードで使う
  - Spring Boot 版は `SkillSheetService` の1つのメソッド（今の `findActiveSheet`）、Go 版は1つの関数
  - 期限切れは 410、未存在は 404
- シートの期限の日数は、管理者が設定する
- エラー
  - `ProblemDetail`（RFC 9457）で返し、フロントが動きを変える種類は `type` で見分ける。`type` の値は実装のときに決める
  - ステータスコード：版が違う 409、同じ冪等キーで中身が違う 422、期限切れ 410、未存在 404、回数制限 429
  - 画面の文は、フロントの固定の文言から出す。`detail` の文は画面に出さない
- 回数制限
  - 保存の処理で新しい行を作ったときだけ、IP ごとに数える。同じ冪等キーのシートを返したときは数えない
  - 組み立て・読み出し・`/status`・ダウンロードには掛けない
  - 上限と時間の幅は、管理者が環境変数で設定する。0 で無効にする
  - バックエンドが1台で動く前提で、メモリに持つ
  - IP の取り方は、実装のときに決める

## 自分の結果ページ

- 開いたとき（再読み込みを含む）は、ストアの回答を組み立ての API に送り、応答の文言つきの回答を表示する
- 共有ビューと PDF は、読み出しの応答を表示する。自分の結果ページと同じ表示の型を使う
- 名前を確定しても、保存はしない
- URL 共有・PDF・CSV を押したときに、それぞれの API を呼ぶ
  - 保存した時点で、名前を固定する。確定後の編集の猶予の途中でも固定にする
  - 回答を直した後に押すと、新しいシートになる。前に共有した URL は、直す前の内容のまま残る
- 印刷は、保存せずに `window.print()` で行う
- 冪等キー
  - 回答と同じストアに持ち、ブラウザに保存する
  - 回答を変える操作（チェック・評価・グループの選択）と、`resetAll` のたびに作り直す。画面の移動と名前の確定では変えない
  - 応答は、送った冪等キーが今の冪等キーと同じときだけ受け取る
  - 422 を受けたら、冪等キーを作り直して1回だけ送り直す
- 409（版が違う）を受けたら、版の確認と同じく `resetAll` で初期値に戻し、一文を出す

## フロントの読み込みと状態

- 読み込み
  - `main.ts` で定義の API の読み込みを待ち、成功・失敗のどちらでもマウントする
  - ルーター（`app.use(router)`）は、読み込みの後に使い始める
  - 起動の順序：定義の API の読み込み → 版の確認 → ルーター → マウント
- 読み込みに失敗したとき
  - `App.vue` で、`<router-view>` の代わりに失敗の画面を出す。URL は変えない
  - ボタンは「再読み込み」（`location.reload()`）だけにする。「トップへ戻る」は置かない
  - 失敗の画面に `data-pdf-error` を付ける
  - ガード（`requiresAnswersGuard` と、回答ページのガード）は判定せずに通す
  - ヘッダーのアプリ名は、固定の文言（「アンケート」）を出す
  - 文言：見出し「読み込みに失敗しました」、本文「一時的な問題で読み込めませんでした。時間をおいて再度お試しください。」、ボタン「再読み込み」
  - 自動でのやり直しはしない
- 定義の API の応答の置き場所
  - 普通のモジュール（`utils/definition.ts`）の変数に入れる。`loadDefinition()` で読み込み、`getDefinition()` で読む
  - 読み込みに失敗したときは、`getDefinition()` が `null` を返す
  - `getDefinition()` は、ファイルの一番上（関数の外）では呼ばない。コメントにそう書く
  - Vue に依存しない関数は、`getDefinition()` を呼ばず、呼び出す側から引数で受け取る
- 設問のデータの型は、定義の API の応答の形をそのまま使う
- 回答の状態
  - 利用者が選んだものだけを持つ。設問の骨組みは持たない
    - TOP で選んだグループ（選べるグループだけ）の `id` の一覧
    - チェックした項目と評価（評価が未選択なら `null`）。キーは、グループ・設問・項目の識別子をつないだ文字列
  - 全員が回答するグループは、状態に持たない。設問のデータの印で判断する
  - 初期値は空。グループのチェックを外したら、そのグループの項目を消す
  - 版（`version`）も持ち、ブラウザに保存する。初期値は今の版
  - 冪等キーも持つ（「自分の結果ページ」）
- 版の確認
  - 判断はストアの外のモジュールで行い、`main.ts` から呼ぶ
  - 版が違えば、ストアの action（`resetAll`）で、名前を含めてすべて初期値に戻す
  - 戻したことの印は、判断するモジュールに持つ（ブラウザに保存しない）
  - 戻したときは「バージョンが変わったため、再度入力をお願いします」の一文を出す

## 画面の固定の文言

- テンプレートに直接書かず、文面の一覧（`src/data/texts.ts`）にまとめる
- CSV の文言は、バックエンドに持つ（「CSV」）
- 表示設定の値の差し込みは、`composables/useTexts.ts` で行う。既定値はバックエンドが当てる
- vue-i18n などのライブラリは入れない
- 対象は、画面に出る文字と `aria-label`。`console` のログと、画面に出ない `Error` の文は対象外
- 表示設定のアイコン（`groupIcons`）は扱わない
- 差し込むのは尺度の名前（`scale.name`）

## 定義ファイルの検証

- 対象は、管理者が定義ファイルを編集するときの書き間違い。配布する完成形（Go 版）を前提に決める
- 段階4より前は、エディタでスキーマが効けば足りる
- 検証は、エディタ（JSON Schema）・コミット時のテスト・起動時の3段で行い、同じ規則を使う
- 形は JSON Schema、スキーマで表せない規則はバックエンドのコードで確かめる
  - コードは検証処理の1か所に置き、起動時・検証コマンド・CI のテストから同じ処理を呼ぶ
- フロントは、起動時の検証を通った定義だけを受け取る前提にし、検証しない
- バックエンドは起動時に `display.json` も検証し、既定値を当ててからフロントに返す。変更は再起動で反映する
- 間違いが1つでもあれば、起動を止める（アイコンのファイルの有無は除く）
- 処理の順序：BOM の除去と文字コードの確認 → JSON として読む（キーの重複の確認を含む）→ スキーマ → コードの規則
- 文字コード
  - UTF-8 だけを受け付ける。先頭の UTF-8 の BOM（`EF BB BF`）は取り除く。UTF-8 として正しくないファイルはエラーにする
  - ライブラリに文字コードを判定させず、自分で処理する
  - Spring Boot 版：BOM を取り除き、`CharsetDecoder`（`CodingErrorAction.REPORT`）で文字列にしてから `JsonMapper` に渡す
  - Go 版：`bytes.TrimPrefix` で BOM を取り除き、`utf8.Valid` で確かめてから `encoding/json/v2` で読む
- 同じオブジェクトの中のキーの重複は、読み込むときにエラーにする
  - Spring Boot 版：定義ファイル専用の `JsonMapper` で `StreamReadFeature.STRICT_DUPLICATE_DETECTION` を有効にする（Spring Boot 全体の `ObjectMapper` は変えない）
  - Go 版：`encoding/json/v2` で読む
- 画面に出す文字列（`plainText`）
  - 空欄・先頭と末尾の空白・制御文字を拒否する
  - 各スキーマの `$defs/plainText` に `pattern` を置き、各項目から `$ref` で参照する
  - `pattern`：`^[^\p{Cc}\p{Zs}]([^\p{Cc}]*[^\p{Cc}\p{Zs}])?$`
  - `\s` は使わず、Unicode の一般カテゴリ（`\p{Cc}`・`\p{Zs}`）を使う
  - 書式の文字（`Cf`。U+200B、U+202E など）は拒否しない
  - `result.heading` と `csv.fileName` は、それぞれの `pattern` に `\p{Cc}` だけを組み込む
  - `plainText` を参照する項目には `minLength: 1` を付けない
- `pattern` を使う項目には、`patternErrorMessage` を付ける
- `pattern` の正規表現は、先読み（`(?=...)`）などを使わない書き方にする

## エラーメッセージ

- 起動時と検証コマンドのエラーは、日本語で組み立てる。検証ライブラリが返す違反の種類と値から文を作る
- 場所は、キーの並びと名前の両方で示す

  ```
  alwaysShownGroups[0].questions[2].items（共通スキル ＞ PC・IT基礎スキル）
    項目が21件あります。20件までにしてください。

  selectableGroups[1].label
    空欄や、先頭・末尾の空白、改行・タブなどの制御文字は使えません。
  ```

- キーの並びは `a[0].b` の形で書き、番号は0から数える
- 名前は、その値が文字列で、その値自体にスキーマのエラーが無いときだけ、その階層の分を括弧に添える。使えない階層は括弧から外す
- 重複のエラーは、場所を1行に1つずつ並べる
- JSON として読み込む前のエラー（キーの重複を含む）は、行と列で示す（例：`survey.json の 12行目 5列目`）。キーの並びも取れるなら添える
- `display.json` のエラーには名前を添えない。`propertyNames` のエラーの場所は、親のオブジェクトまでになってよい
- エラーの表示順は保証しない。共用するテスト用の定義で期待するエラーを比べるときは、順序によらない比べ方にする
- 定義の値をエラーの文に入れるときは、制御文字を `\n` や `\u001b` のような見える表記に置き換える。置き換えは、エラーの文を組み立てる1か所で行う

## JSON Schema の書き方

- Draft 2020-12 で書く。draft-07 には下げない
- v1 が公開されたら移行を検討する。移行するときは、`patternErrorMessage` が使えるかを確かめ直す
- 定義ファイルの `$schema` は相対パスで書き、スキーマのファイルを配布物に同梱する
- `$comment` は書かない（`plainText` の説明だけは `$comment` に書く）。解説は README に書く
- `description` は、句点を付けない短い文にする。`plainText` には書かない
- `plainText` を参照する項目にも、`"type": "string"` を書く
- グループの定義は、`properties` を各定義に書き、値だけを `$defs` から参照する。`allOf` での取り込みと `unevaluatedProperties` は使わない
- `format` は既定で検証されない。足すときは、エラーにならないことに注意する
- `result.heading` の `{name}` がちょうど1つという規則は、`pattern`（`^[^{}]*\{name\}[^{}]*$`）で表す

## DB とデータ

- マイグレーションは1つの V1 にまとめ直し、新しいテーブルで始める
  - 段階6で新しい DB に切り替える。旧アプリの回答は引き継がない
  - 開発環境では、`docker compose down -v` でボリュームを消してから使う
- シートは1行で持ち、回答は文言つきの回答として jsonb の列に入れる。グループと回答の子テーブルは持たない
- 文言つきの回答の形

  ```json
  {
    "groups": [
      {
        "id": "common",
        "label": "共通スキル",
        "questions": [
          {
            "id": 1,
            "title": "コミュニケーションツール",
            "items": [{ "id": 1, "label": "Slack", "value": 4 }]
          }
        ]
      }
    ]
  }
  ```

  - キーは定義の API に揃え、項目に `value` を足す
  - 入れるのは、チェックして値のある項目だけ。項目が1つも無いグループと設問は入れない
  - 全員が回答するグループかの印は入れない

- シートのテーブルの列（列とテーブルの名前は、実装のときに決める）

  | 列           | 型                                        | 内容                                       |
  | ------------ | ----------------------------------------- | ------------------------------------------ |
  | `id`         | `uuid`                                    | シートの ID。共有 URL とダウンロードに使う |
  | 冪等キー     | `uuid`（一意の制約、`not null`）          | フロントが作る UUID                        |
  | `user_name`  | `text`（`not null`）                      | 名前。長さはアプリで確かめる               |
  | `answers`    | `jsonb`（`not null`）                     | 文言つきの回答                             |
  | `created_at` | `timestamptz`（`not null`）               | 作った日時                                 |
  | `expires_at` | `timestamptz`（`not null`、インデックス） | 期限。定期削除で使う                       |
  - 日時は、アプリでは UTC の時刻で扱う（Spring Boot 版は `Instant`、Go 版は `time.Time`）

- シートのテーブルに、版の列と `share_token` の列は持たない
- `AnswerDto.value` に `@NotNull` を付ける（段階4で DTO を作り直すとき）

## PDF 生成

- 描画は、結果ページを Chromium で開いて印刷する。画面と PDF で描画を分けない
- 描画の口（`PdfRenderer`）を共通にし、描画役ごとに実装を差し替える
  - PDF 用のコンテナ：HTTP で頼み、PDF を応答の本文で受け取る
  - Lambda：同期の呼び出しで頼む。PDF の受け取り方は、呼び出し方とあわせて実装のときに決める
- 配布する Go 版は、PDF 用のコンテナを使う。Lambda は、求められたら足す
- Spring Boot 版は両方を持つ。開発環境は PDF 用のコンテナ、公開デプロイは Lambda を使う
- API とフロントの動きは、版や描画役によらず揃える
- フロントとバックエンドの間は、依頼とポーリングの形にする。バックエンドは、裏の処理で描画役の終わりを待つ
- 生成は、PDF のボタンを押したときに、PDF 生成の API（「シートの API」）で依頼する。再試行も同じ API を使う
- 依頼は、保存の処理のコミットの後に行う
  - Spring Boot 版は、トランザクションの外のメソッドから、保存のメソッド（`@Transactional`）と依頼を順に呼ぶ
  - Go 版は、コミットしてから依頼の関数を呼ぶ
- PDF は DB の別の表（`sheet_pdfs`）に持つ。シートの ID を外部キーにし、`on delete cascade` でシートと一緒に消す
- 配信は、バックエンドのダウンロード用のエンドポイントで行う。S3 は使わない
- 完了は `sheet_pdfs` の行の有無で判断し、生成中と失敗はバックエンドのメモリに持つ
- `/status` は状態（ready・generating・failed）だけを返す。ダウンロードの URL は返さない。記録が無い場合は failed として扱う
- `/status` とダウンロードは、先にシートの有無と期限を確かめる（「シートの API」）
  - `/status` の判定の順序：シートの確認 → 行がある → ready、生成中 → generating、それ以外 → failed
- 二重の生成の防止は、状態で判定する
  - 依頼のとき：「無いか失敗なら生成中にし、そうでなければ何もしない」を1回の操作で行い、その後で `sheet_pdfs` の行を確かめる。行があれば状態を消して終える
    - Spring Boot 版は `ConcurrentHashMap.compute`、Go 版は `sync.Mutex` のロックの中で行う
  - 生成の処理：描画 → `sheet_pdfs` に保存 → コミットの後にメモリの状態を消す。例外なら失敗にする
  - 依頼の入口は、PDF 生成の API だけにする。`regenerate` は持たない
  - PDF 生成の API は、保存の処理を通った後は、PDF の状態（生成中・完了・失敗）によらず 202 を返す。保存の処理のエラーは、ほかの共有操作と同じに返す
  - `LambdaPdfService` の `lastInvokedAt` と、その定期削除は無くす
  - バックエンドが1台で動く前提（`SaveRateLimiter` と同じ）
- 描画役に同時に頼む数の上限は、バックエンドで掛ける。Lambda のときも同じ仕組みにする
  - 件数に上限のある待ち行列で待たせ、あふれたら失敗にする
  - Spring Boot 版は PDF 専用の `ThreadPoolTaskExecutor`（スレッド数＝同時に頼む数、`queueCapacity`＝待ち行列の数）。あふれたときの `TaskRejectedException` で失敗にする
  - Go 版は、容量つきのチャネル（待ち行列）と、同時に頼む数だけ起動した goroutine。`select` の `default` で、あふれたら失敗にする
  - 同時に頼む数と待ち行列の数は、環境変数で設定する。既定値は、描画役を決めてメモリの使い方を測ってから決める
- 描画役
  - PDF 用のコンテナは Gotenberg（Chromium だけのイメージ、9系）を使う
  - Lambda も Gotenberg の Lambda 向けイメージにそろえる（仮決定）。実装で問題が出たら、Spring Boot 版の Lambda は `aws-lambda/` の実装を、PDF を同期で返す形に書き換えて使う

## CSV

- CSV の API（「シートの API」）は、保存の処理を通してから、ダウンロードの URL を返す
- ダウンロード用のエンドポイントは、シートの ID で、保存した文言つきの回答からその場で作って返す
- ファイル名は、`Content-Disposition` で指定する
- ボタンは自分の結果ページにだけ出す。共有ビューには出さない
- ファイル名の `{date}` は、サーバーの時刻で決める。時間帯は、コンテナの時刻の設定で合わせる
- 式として解釈される先頭の文字のエスケープは、バックエンドで行う
- 固定の文言：1行目の見出しは「名前」。「カテゴリ」「質問項目」は今のまま
